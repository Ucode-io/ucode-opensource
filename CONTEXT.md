# CONTEXT

Глоссарий домена ucode. Единственный источник правды по терминам.
Здесь нет решений о реализации — только значения слов.

## Table

Схема данных: набор Field'ов и связей. Идентифицируется `slug`.
Не содержит данных — только описание их структуры.

Не называть: Object, Collection, Entity.

## Item

Одна запись данных внутри [[Table]].

Бэкенд называет одно и то же двумя словами: `object` (старая версия API)
и `item` (новая). Канон — **Item**, потому что мы живём только на новой версии.

Не называть: Object, Record, Row, Data. `Object` и `Record` — встроенные
типы TypeScript, ими нельзя назвать интерфейс.

## Field

Поле в схеме [[Table]]: имя, тип, валидация, настройки.
Свойство схемы. Существует независимо от того, показан ли он на экране.

Не путать с [[Column]].

## FieldOption

Вариант выбора у [[Field]] типа `STATUS` или `MULTISELECT`. В базе два
типа хранятся по-разному, и это не случайность — у них разные экраны
настройки. Наружу отдаётся одна форма: ключ поиска всегда `value`.

| | MULTISELECT | STATUS |
|---|---|---|
| Где лежат | `attributes.options[]` | `attributes.{todo,progress,complete}.options[]` |
| Что сохранено в [[Item]] | `option.slug` | `option.value` |
| `option.value` | подпись на базовом языке, **не значение** | значение |
| `option.label` | есть | **нет** |
| Подписи по языкам | `label_<код языка данных>` | `label_<код языка данных>` |
| Цвет | `option.color`, HEX | `option.color`, HEX |

Ловушка: искать вариант по `option.value` для обоих типов. Для
MULTISELECT это никогда не совпадёт — там в `value` лежит подпись.
Старый ucode делал именно так, и ячейка MULTISELECT теряла и цвет,
и перевод. Правильный разбор у него есть, но в другом месте —
в генераторе фильтров, а не в рендере ячейки.

Вторая ловушка: у STATUS `attributes.options` существует и всегда пуст.
Варианты лежат в трёх списках по стадиям.

Цвет — HEX из данных. В интерфейсе он не рисуется: читается как
намерение («красный») и переводится в оттенок палитры, у которого
контраст проверен в обеих темах. Актуальная форма создания поля уже
предлагает выбор из четырёх именованных цветов, а не пипетку.

## Column

[[Field]], показанный в конкретном [[View]]: ширина, позиция, видимость,
закреплённость. Свойство отображения.

Один Field может быть Column'ом в одном View и отсутствовать в другом.
Column без Field не существует.

## View

Сохранённая конфигурация отображения данных одной [[Table]]:
какой [[ViewType]], какие [[Column]], фильтры, сортировка, группировка.

Принадлежит Table. У одной Table может быть много View.

Не называть: Layout, Tab, Screen.

## Default filter

Отбор, записанный в настройках [[View]] (`attributes.default_filters`).

**Это область видимости, а не начальное значение.** Применяется всегда
и перекрывает собственный фильтр человека по тому же полю. Админ ставит
«только активные записи» и вправе рассчитывать, что снять это нельзя.

Отсюда два следствия в интерфейсе:

- в подшапке такого поля нет — чип по нему выглядел бы рабочим,
  а условие всё равно перекрывалось бы настройкой;
- в счётчике фильтров он считается: список неполный, и на экране это
  должно быть отмечено, даже когда снять его нечем.

Настраивается по ВСЕМ полям таблицы, а не по показанным [[Column]]:
видимость колонки на область видимости не влияет, а условие, заданное
по скрытому полю, иначе стало бы неснимаемым.

Не путать с `attributes.quick_filters` — вот **это** подсказка: набор
полей, которые админ предлагает чипами. Их человек и добавляет, и снимает.

## ViewType

Способ отображения, который выбирает View: `TABLE`, `BOARD`, `CALENDAR`,
`TREE`, `TIMELINE`.

`GRID` — упразднён. Существовал только потому, что старый TABLE не тянул
большие объёмы данных, и его заменили на ag-grid как отдельный тип.
С виртуализацией в TABLE второй табличный тип не нужен. У пользователя
остаётся **один** табличный ViewType — `TABLE`.

## Project

Рабочее пространство пользователя: набор [[Table]], настроек и окружений.
Принадлежит компании. Идентифицируется UUID — slug'а у Project нет,
`name` произвольный и не URL-safe.

## Environment

Изолированный экземпляр данных внутри [[Project]] (prod, dev, ...).
У Table одна схема на Project, но данные ([[Item]]) свои в каждом Environment.

Хранится **в серверной сессии**, а не в токене и не в URL. Из-за этого
пользователь одновременно находится ровно в одном Environment — во всех
вкладках браузера сразу. См. [[Session]].

## Session

Серверная запись, связывающая User × [[Project]] × [[Environment]] × Role ×
ClientType. «Залогинен» — это не булево, а именно этот кортеж.

Смена Environment мутирует ту же запись сессии и выпускает новую пару
токенов. Поэтому смена окружения — переход, а не переключатель.

## Locale

Язык интерфейса админки (ru, en, uz). Свойство пользователя, не данных.
Не путать с [[Multilanguage Field]].

## Multilanguage Field

[[Field]] с включённым `enable_multilanguage`. Список языков задаётся
на уровне [[Project]] — см. [[Data Language]].

**Это не одно поле с картой значений по языкам.** Это НЕСКОЛЬКО [[Field]],
по одному на язык, и код языка дописан к слагу через подчёркивание:
`title_en`, `title_cyr`. Признак `enable_multilanguage` стоит у каждого
из них. В схеме таблицы они приходят отдельными полями и отдельными
колонками в базе.

Так их и разбирает бэкенд: раскладка карточки запрашивается с параметром
`language_setting`, и поля отсеиваются по суффиксу
(`object_builder/storage/postgres/layout.go:549` —
`strings.HasSuffix(field.Slug, "_"+req.LanguageSetting)`).

Собирать их обратно в одно поле нужно на клиенте, иначе карточка
показывает три соседние строки с одинаковой подписью. Место сборки одно
— `features/table/model/multilanguage`.

Ловушка: код языка нельзя отрезать «всё после последнего подчёркивания».
`order_id` тогда становится полем `order` на «языке» id. Отрезается
только код из списка языков проекта.

Свойство данных, не интерфейса. Пользователь с [[Locale]] `en` может
редактировать узбекское значение поля.

## Data Language

Язык из набора, заданного [[Project]] (`GET /v1/company-project/{id}` →
`language[]`). Код языка — `short_name`. Им размечены подписи
[[FieldOption]] (ключ `label_<код>`), имена [[View]] (`name_<код>`)
и слаги [[Multilanguage Field]] (суффикс `_<код>`).

**Это не [[Locale]].** Набор кодов задаёт проект, и с ru/en/uz он не
обязан совпадать: в живом проекте это `en` и `cyr` («Uzbek (Cyrillic)»).
Отсюда ключи `label_cyr` — они про узбекскую кириллицу, а не про русский.

Старый ucode при загрузке насильно переключал i18n на первый язык
проекта — интерфейс уезжал в язык данных. Повторять нельзя: две оси,
две настройки.

**Как читается подпись.** Ключи `label_<код>` и `name_<код>` — это
надписи интерфейса (имя пункта меню, подпись колонки, имя вкладки),
поэтому читаются по двум осям, в порядке: [[Locale]] → Data Language →
базовая колонка (`label`, `name`). Переключение языка интерфейса
обязано переводить меню и колонки — так это работает в старой админке
(`attributes[label_${i18n.language}]`), — а вторая ступень спасает
проекты, где локали нет среди языков проекта. Реализация одна:
`features/table/model/types.ts`, `localized`.

**Значения** мультиязычного поля выбирает только Data Language:
это данные, а не надписи, и локаль интерфейса на них не влияет.

Единственное истинное имя признака — `field.enable_multilanguage`
(колонка в БД и поле proto). Варианты `enable_multi_language` и
`attributes.enable_multi_language` — мусор, читать их нельзя.

## Relation

Связь между двумя [[Table]]. Со стороны UI проявляется как [[Field]]
особого типа, значение которого — ссылка на [[Item]] другой Table.

Что показать вместо uuid, задаёт `relation.view_fields` — слаги полей
**целевой** таблицы. Значения берутся из связанной строки, которая
приходит рядом со ссылкой: `author_id` → `author_id_data`.

Если `view_fields` не настроены, показывать нечего — ячейка пустая.
Подставлять `title`, `name` или guid нельзя: это угадывание, а не
чтение. У ненастроенной связи бэкенд кладёт в `view_fields` само
поле-связь исходной таблицы — такие отбрасываются.

В [[View]] колонка-связь указывается **id связи**, а не id поля
(`field.relation_field`). Колонки ищутся по обоим ключам; без этого
у таблицы со связями молча пропадают колонки.

## Relation tab

Вкладка в карточке [[Item]], показывающая строки ЧУЖОЙ таблицы,
связанные с открытой записью.

Это [[View]] пункта меню с `is_relation_view: true`, а не вкладка
раскладки. Так её заводит и показывает старая админка, и так она
получает всё то же, что и обычный view: собственные колонки, отбор
по умолчанию, чипы фильтров, закреплённые колонки и имя по языкам.
У вкладки раскладки (`layout.tabs` с `type: "relation"`) из этого нет
ничего: PUT раскладки сохраняет у вкладки только `id, label, type,
order, icon, relation_id, attributes`.

**Вкладки раскладки не показываются.** Бэкенд заводит такую вкладку
САМ на каждую Many2One (`pkg/helper/relation.go`) — вместе с безымянным
view той же связи, — и в карточке появлялись все связи таблицы разом,
включая те, что показывать никто не просил. Цена решения: в проекте,
где relation view не заводили, карточка остаётся без вкладок связей,
пока их не добавят кнопкой «+».

**Свою связь вкладка ищет по `relation_id`, потом по
`relation_table_slug`.** Форма старой админки `relation_id` не шлёт,
поэтому у заведённых ею вкладок он пуст, и связь приходится искать
по слагу чужой таблицы; с двумя связями на одну таблицу («склад
отправитель» и «склад получатель») выбрать из них нельзя, и берётся
первая. Свои вкладки мы создаём с `relation_id` — тогда однозначно.

Колонка-ссылка берётся из ручки связей (`field_from` /
`relation_field_slug`), а не собирается как `<слаг таблицы>_id`:
у второй связи на ту же таблицу имя другое, и собранное промахивается.
Сторону определяет сравнение с нашим слагом:

| Мы | Что показывает вкладка | Где ссылка | Создание |
|---|---|---|---|
| `table_to` | строки `table_from` | у них, `field_from` | привязывается сама |
| `table_from` | одну строку `table_to` | у нас, `field_from` | не создаём: привязка — правка НАШЕЙ строки |

## Action

Функция проекта, которую запускают над отмеченными [[Item]] из таблицы.
Кнопка-молния над списком.

Одна сущность под тремя именами: ручка зовётся `automation`
(`/v2/collections/{slug}/automation`), таблица в базе — `custom_event`,
старая админка — Actions. Канон — **Action**.

`event_path` — это id функции, а не путь. Зовётся она той же ручкой,
что и поле-кнопка: `POST /v1/invoke_function`. Признак «выключено»
называется `disable`, без «d» на конце.

## Navigate URL

Адрес, которым экран подменяется страницей самого проекта. Три штуки,
все в `view.attributes`:

| Ключ | Что подменяет |
|---|---|
| `navigate` | щелчок по строке — вместо карточки |
| `url_object` | «новая запись» — вместо строки в таблице |
| `pdf_url` | печатная форма записи — кнопка в карточке |

Адрес — шаблон: `{{$слаг}}` подставляется значением поля строки. У первых
двух рядом лежат `params` — пары «ключ — значение» для строки запроса,
и оба конца тоже шаблоны.

Ловушка: настройки старой админки пишут объект `{url, params}`, а её же
экраны читают `attributes.url_object` как строку. В проектах лежит и то,
и другое — читаются оба вида.

## Autofill

[[Field]], значение которого берётся из строки, на которую указывает
[[Relation]]: «телефон клиента» заполняется из выбранного клиента.

Настройка лежит на поле-приёмнике тремя **колонками**:
`autofill_table` — «чужая таблица#колонка-связь в нашей таблице»,
`autofill_field` — слаг поля чужой таблицы, `automatic` — подставлять
сразу или только в пустое.

Источником может быть только Many2One нашей стороны: подставлять не из
чего, пока связанная строка не приходит вместе с нашей, а приходит она
ровно у таких связей (`client_id` → `client_id_data`).

## Запрещённые имена в коде

| Слово | Почему | Вместо него |
|---|---|---|
| `views/` как имя папки | Коллизия с доменным [[View]]. В старом коде дошло до `src/views/views/` | `routes/` — для страниц |
| `Object` | Занято в TypeScript; в домене означает [[Item]] | `Item` |
| `GRID` | Упразднённый [[ViewType]] | `TABLE` |
| `enable_multi_language`, `attributes.enable_multi_language` | Не существуют в схеме. Признак называется `enable_multilanguage` | `enable_multilanguage` |
| `attributes.enable_multilanguage`, `attributes.autofill_table`, `attributes.autofill_field`, `attributes.automatic` | Эхо: бэкенд копирует туда колонки, отдавая layout. Пишутся и читаются только колонки | одноимённые колонки [[Field]] |
| `new_design`, `new_router`, `new_layout` | Поля Project в бэкенде, различавшие поколения UI. Новый фронт их не читает и всегда работает как «новая версия» | — |
