# Что не так в бэкенде

Список мест, которые фронт обходит. Правим не мы — репозиторий чужой
(см. CLAUDE.md, «Бэкенд — только чтение»), поэтому здесь только адрес
и суть. Каждый обход в коде помечен комментарием со ссылкой сюда или
прямо на строку в Go.

Пути даны от `ucode_backend/`.

## Таблица

**Слаг таблицы не обновляется.** `ucode_go_object_builder_service/
storage/postgres/table.go:887` — в `UPDATE "table" SET …` колонки `slug`
нет вовсе. Старая админка показывала поле ввода «KEY», принимала новый
слаг и отвечала «сохранено», не меняя ничего. У нас слаг показан
и не правится.

**Таблица входа перезаписывает свои настройки.** Там же, `table.go:1007`:
при `is_login_table = true` бэкенд собирает `auth_info` сам —
`role_id: "role_id"`, `client_type_id: "client_type_id"` (строками,
не идентификаторами), а поля логина, пароля, почты и телефона заводит
по списку `login_strategy`. Шесть выпадающих списков старой админки
не значили ничего: сохранялось не то, что в них выбрали.

Там же: без непустого `attributes.auth_info.login_strategy` ручка
отвечает отказом «login_strategy does not exist» (`table.go:970`).
Поэтому включение таблицы входа доезжает до сервера только вместе
с первым выбранным способом.

**GET /v3/…/tables/{collection} читает не тот параметр.**
`ucode_go_admin_api_gateway/api/handlers/v3/table.go:131` берёт
`c.Param("table_id")`, а маршрут объявлен как `/:collection`
(`api/api.go:915`). Параметр всегда пустой. Поэтому настройки таблицы
мы читаем ручкой v1.

## Поле

**`enable_multilanguage` не сохраняется при создании.**
`ucode_go_object_builder_service/storage/postgres/field.go:116` —
колонки нет в списке INSERT. Шлюз по этому признаку заводит по колонке
на каждый язык проекта (`api/handlers/v2/field.go:84`), но сам признак
у созданных полей остаётся `false`. Из-за этого языковую группу
приходится опознавать по форме набора — см. ADR-0004.

**PUT поля не заводит языковые колонки.** Признак включается, колонок
`title_en`/`title_cyr` не появляется. Отсюда: мультиязычность
спрашивается только при создании.

**Права роли на поля отдаёт только раскладка.** В запросе GET /v2/fields
колонок `view_permission` и `edit_permission` нет вовсе — схема приходит
одинаковой для всех ролей. Единственное место, где они подставляются
по роли из токена, — `GET /v2/collections/{slug}/layout/{menu}`
(`storage/postgres/layout.go:967`, `getFieldsWithPermissions`). Поэтому
права накладываются на схему уже на фронте.

**Раскладка чужой таблицы отдаётся по любому `menu_id`.** GET требует
непустой `menu_id`, но если раскладки для этой пары нет, отдаёт общую
(`layout.go:1197`: не нашли по `menu_id` — берём `is_default`). На этом
держатся вкладки связей: права полей чужой таблицы считаются по
таблице и роли, а не по раскладке, поэтому запрос с нашим `menu_id`
возвращает их верными. Писать такую раскладку нельзя: PUT пишет
`menu_id` безусловно и привязал бы общую раскладку к нашему пункту меню.

**У роли без записей в `field_permission` раскладка приходит пустой.**
Тот же запрос: `LEFT JOIN "field_permission" fp … WHERE t.slug = $1 AND
fp.role_id = $2` — условие на присоединённую таблицу в WHERE превращает
LEFT JOIN во внутренний, и поля без строки прав из ответа выпадают.
Отсюда правило на фронте: прячется только то, что запрещено явно,
а не «всё, чего нет в раскладке».

**`defaultValue` бэкенд не подставляет — ветка для него недостижима.**
Колонки `default` у поля нет, ключ лежит в свободном мешке `attributes`,
и читает его условие `if ok2 && !ok` (`prepareFunctions.go:216`), где
`ok` — «ключ есть в присланных данных», а `ok2` — «значение непустое».
Оба сразу невозможны: при отсутствующем ключе значение равно `nil`,
а `IsEmpty(nil)` возвращает `true` (`helper/items.go:944`). Живёт
только соседняя ветка — `default_values[0]`, список под прежним именем
того же ключа, и только когда поле не прислано.

Значение по умолчанию — настройка фронта (`blankItem`). В записи,
заведённой мимо админки, `defaultValue` не подставится; `default_values`
подставится.

**Пароль длиной ровно 60 символов сохраняется открытым текстом.**
PASSWORD хэшируется при вставке и правке строки
(`storage/postgres/items.go:668`, `:1669`), но под условием
`if len(password) != config.BcryptHashPasswordLength` — то есть «не 60,
значит ещё не хэш». Проверка нужна, чтобы повторная отправка уже
хэшированного значения не захэшировала его дважды, но длина — плохой
признак: bcrypt-хэш действительно 60 символов, и живой пароль такой же
длины ляжет в колонку как есть. Ни ошибки, ни следа в логе.

Фронт этого не обходит и не может: длину пароля выбирает человек. Окно
«задать пароль» шлёт значение обычной правкой строки и старое в ответ
не отправляет (`ItemDrawer`, `PasswordDialog`).

**RANDOM_TEXT без `digit_number` вешает вставку.**
`ucode_go_object_builder_service/pkg/helper/prepareFunctions.go:59` —
цикл `for { }` крутится, пока сгенерированная строка пуста, а
`GenerateRandomString(prefix, 0)` при пустой приставке всегда возвращает
пустую (`pkg/helper/generator.go:26`). Не таймаут, а бесконечный цикл
в обработчике.

Обход: длину таких полей фронт отправляет всегда и никогда нулём —
пустое поле ввода превращается в шесть (`api/fields.ts`, `lengthOf`).
Поля, заведённые мимо админки, это не спасает.

**Генерируемое поле в таблице может быть только одно на тип.**
`storage/postgres/items.go:243` складывает поля в `map[тип]поле`, поэтому
из двух INCREMENT_ID (или MANUAL_STRING, RANDOM_TEXT — всё из
`config.Ftype`) заполнится только последнее, а первое останется пустым.
Молча.

**Шаблон MANUAL_STRING подставляется без границ слова.**
`pkg/helper/prepareFunctions.go:87` идёт по слагам таблицы и делает
`strings.ReplaceAll(text, slug, value)` — в произвольном порядке
и без сортировки по длине (у FORMULA_FRONTEND она есть,
`formula_service.go`). Поэтому в таблице со слагами `name` и `name_ru`
шаблон `name_ru` превратится в «<значение name>_ru». Собирается
значение один раз, при вставке: правка шаблона старые строки
не пересчитывает.

**Правка формулы не пересчитывает уже сохранённые строки.**
`FORMULA_FRONTEND` бэкенд считает сам и пишет результат в колонку
(`storage/postgres/formula_service.go:107`, запись — `:133`), а
пересчёт зависимых строк — `RecalculateAffectedFormulas` (`:168`) —
зовётся только из работы со строкой: вставка (`items.go:552`), правка
(`:850`), удаление (`:1269`). От правки самого поля не зовётся никто,
так что новая формула начинает действовать со следующего сохранения
каждой строки, а до него в колонке лежит число, посчитанное по старой.
Тот же класс, что у шаблона MANUAL_STRING выше.

Фронт этого не обходит: ячейка показывает то, что в колонке, — иначе
экран разошёлся бы с фильтром и сортировкой
(см. [FIELD-AUDIT](FIELD-AUDIT.md), F22).

**Приставка приклеивается через дефис, даже когда её нет.** У
RANDOM_NUMBERS значение собирается как `prefix + "-" + число`
(`generator.go:21`) без проверки на пустоту — поле без приставки
получает значения вида `-4821`. У INCREMENT_ID та же склейка сделана
с проверкой, поэтому там пусто значит пусто.

## Связи

**Many2Many пишется только при вставке.** Список лежит денормализованно
в обеих таблицах — колонками `<чужая таблица>_ids`, — и симметрию
бэкенд поддерживает ровно в одном месте: `helper.AppendMany2Many`
(`pkg/helper/items.go:749`), которое зовётся из Create. Обычный
`PUT /v2/items` пишет только ту колонку, что пришла в теле
(`storage/postgres/items.go:607` — SET по полям запроса), поэтому правка
списка с одной стороны оставляет вторую со старым набором.

**Ручки many-to-many для postgres не реализованы.**
`PUT /v2/items/many-to-many` и `DELETE /v2/items/many-to-many` есть
в маршрутах, но в обработчике ветка `ResourceType_POSTGRESQL` отвечает
`400 "does not implemented"` (`api/handlers/v2/items.go:2232`, то же
в v1 и v3). Работают они только у mongo-проектов. Отсюда: связать
и развязать Many2Many из таблицы нечем, и такие поля у нас только
читаются.

**Many2Dynamic на postgres-проекте не работает у самого бэкенда.**
Связь на таблицу, выбираемую в строке, ломается в трёх местах:

- `Create` (`storage/postgres/relation.go:71`) в ветке
  `case config.MANY2DYNAMIC` присваивает `fieldFrom` и всё; блок,
  создающий поле и колонку, обёрнут в `if resp.Type !=
  config.MANY2DYNAMIC` (`:704`). В базу попадает только строка связи —
  колонки для значения `{"<слаг>_id": guid}` не появляется;
- `layout.go:660` кладёт `dynamic_tables` в атрибуты поля как
  `fmt.Sprintf("%v", …)` от Go-карты, то есть строкой
  `map[table_slug:cities view_fields:[name]]` вместо объекта;
- `GetSingleViewForRelation` в ветке Many2Dynamic собирает запрос
  с лишней запятой: `SELECT id, slug, table_id , attributes,  FROM
  field` (`relation.go:2776`) — он не выполнится никогда.

Обойти на фронте нельзя: кривой ответ разобрать можно, отсутствующую
колонку — нет. Поэтому связей мы заводим только Many2One (см.
`features/table/model/relation-draft`), и это второе основание к тому,
что уже там записано.

## Раскладка карточки

**У связи не приходит почти ничего.** GET
`/v2/collections/{slug}/layout/{menu_id}` отдаёт `tabs[].relation`
только со сторонами (`table_from`, `table_to`), типом и `view_fields`:
`GetRelation` (`storage/postgres/layout.go:1628`) больше ничего
не выбирает. Ни `relation_field_slug`, ни прав, ни колонок там нет —
и `relation_table_slug` бэкенд подставляет как `table_from.slug`,
то есть у одной из сторон он называет чужой таблицей её саму.

Поэтому вкладки карточки строятся не по раскладке, а по view пункта
меню, а колонка-ссылка берётся из ручки связей — см. CONTEXT,
Relation tab.

**PUT раскладки сохраняет у вкладки девять колонок.** `id, label,
layout_id, type, order, icon, relation_id, attributes, view_type`
(`storage/postgres/layout.go:55`) — всё остальное, что положили в тело
вкладки, молча пропадает вместе с ответом 200. Колонки вкладки,
записанные в `relation.columns`, держались ровно до перезапроса.

**Имя секции пишется, но не возвращается.** PUT кладёт `section.label`
в колонку (`storage/postgres/layout.go:59` — она в списке колонок
вставки), а запрос секций выбирает только `id`, `"order"`, `fields`
и `attributes` (`layout.go:1367`, `GetSections`). Этим же запросом
обслуживаются и GET по пункту меню, и список раскладок, так что имя
секции не приходит НИКОГДА: переименованная секция после перезапроса
снова безымянная. Обходим дублированием имени в `section.attributes.label`
— он ездит в обе стороны (`features/item/model/layout`, `LayoutSection`).

**`is_summary_section` не возвращается тем же запросом** и по той же
причине. Плюс `layout.summary_fields` из proto не заполняется ниоткуда:
ни `GetAllV2`, ни `GetSingleLayout` (`layout.go:1219` и `1135`) этого
ключа в `jsonb_build_object` не собирают вовсе. Сводной секции в ответе
нет ни под одним именем.

Заполняет `SummaryFields` только `GetAll` (`layout.go:763`) — **и это
мёртвый код**: grpc-метод `Layout().GetAll` зовёт `GetAllV2`
(`grpc/service/layout.go:51`), так что в `GetAll` не заходит никто.
Читая эту функцию, легко решить, что сводная секция приезжает; её
`SELECT` — единственный в файле, где есть и `menu_id`, и путь
к `summary_fields`, и ни то, ни другое до фронта не доходит.

`is_summary_section` умеет выбирать ещё `sectionRepo.GetAll`
(`storage/postgres/section.go:63`), но наружу он не выведен: у `Section()`
шлюз зовёт только `GetViewRelation` и `UpsertViewRelations`.

**Список раскладок не говорит, чья раскладка.** `GET
/v2/collections/{slug}/layout` (`GetAllV2`, `layout.go:1229`) отдаёт
`id`, `label`, `type`, флаги и вкладки — но не `menu_id`. А прочитать
раскладку по её собственному id нельзя: у шлюза есть только GET
по `menu_id` (`api/api.go:641`). Метод `Layout().GetByID` в сервисе
есть, но шлюз зовёт его лишь внутри `UpdateLayout`
(`api/handlers/v2/layout.go:405`, `v3/layout.go:376`), маршрута наружу
нет. Выбрать раскладку для пункта, значит, не из чего.

Старая админка это и не выбирает: `NewlayoutList.jsx:128` группирует
раскладки по `layout?.menu_id`, а грузит их тем же `GET
/v2/collections/{slug}/layout` — поле всегда `undefined`. Экран
сломан и в референсе.

**Иконка вкладки теряется при любой правке раскладки.** GET её
не отдаёт (в `jsonb_build_object` вкладки ключа `icon` нет), а PUT
пишет колонку безусловно — то есть пустой строкой.

**У каждой связи есть безымянный view.** Он создаётся вместе со связью
(`pkg/helper/relation.go:335`) с пустым `name` и без `menu_id`, поэтому
«у связи есть view» ничего не отсеивает, а `relation.title` в списке
связей у таких пуст.

## Авторизация

**Восстановление пароля — четыре ручки, и одной из них нет в исходниках.**
`POST /v2/forgot-password`, `PUT /v2/set-email/send-code`
и `PUT /v2/reset-password` лежат в `ucode_go_auth_service/api/api.go`,
а `POST /v2/verify-only-email` — нет: его зовёт старая админка
(`services/auth/authService.js`), и он отвечает на том же хосте, но
ни в одном из наших репозиториев его нет. Контракт взят из старого
клиента:
тело `{sms_id, otp, register_type: "default"}`, ответ `{verified}`.

**Отказа на первом шаге не бывает.** Все три исхода приходят со статусом
200: код ушёл (`email_found: true`), почты у пользователя нет
(`email_found: false` при непустом `user_id`) и логина нет вовсе
(пустой `user_id`). Различать их приходится по полям.

**Регистрация по приглашению падает на пустом поле.**
`POST /v2/register` читает `type`, `client_type_id` и `role_id`
приведением типа без проверки (`register_v2.go:408` —
`body.Data["type"].(string)`), поэтому тело без любого из них роняет
обработчик, а не возвращает 400.

## Таблицы и права

**Удаление таблицы есть только в v2.** `DELETE /v3/.../views/{view}/tables/{collection}`
читает `c.Param("table_id")`, которого в этом маршруте нет (`api/handlers/v3/table.go:473`),
и всегда отвечает «table id is an invalid uuid». Рабочая ручка —
`DELETE /v2/collections/{id}`, и в пути ей нужен именно id: слаг она
отклоняет проверкой на uuid.

**Удаление таблицы уносит и пункт меню.** Одна транзакция
(`storage/postgres/table.go`, Delete): строка `table`, `DROP TABLE`,
раскладки с вкладками и секциями, связи в обе стороны, права на поля
и записи, view и `menu` с этим `table_id`. Системную таблицу удалить
нельзя, но признака `is_system` в ответе о таблице нет — заранее спрятать
действие не по чему.

**Ответ прав роли завёрнут дважды.** Под общим конвертом лежит
`{project_id, data: {...}}`, и права — в этом `data`: там же `guid`
и `name` роли, `tables[]` и `global_permission`. Отдельного объекта
`role` в ответе нет. Список ролей (`GET /v2/role`) устроен ещё иначе —
`{table_slug, data: {count, response}}`, как ручки строк таблицы.

**`is_public` в ответе прав не приходит.** Старый экран рисует под него
колонку, но `record_permissions` содержит только read/write/update/delete
(проверено на живом проекте). У `custom_permission` пятнадцать ключей,
у `global_permission` — семнадцать, и они БУЛЕВЫ, в отличие от прав
на таблицы.

**Права роли перезаписываются целиком.** `PUT /v2/role-permission/detailed`
отказывается работать без `global_permission` (`storage/postgres/permission.go:1202`)
и ждёт обратно весь объект, который отдал GET. Значения прав — строки
`'Yes'`/`'No'`, а не булевы: `"No"` в булевом контексте истинна.
`project-id` при этом читается из строки запроса, а не из тела.

## Действия (automation)

**Поле называется `disable`, без «d» на конце.**
`ucode_go_admin_api_gateway/api/models/custom_event.go:9`. Форма старой
админки писала `disabled` — выключить действие через неё было нельзя.

**Отказ функции приезжает со статусом 200.** `POST /v1/invoke_function`
отвечает `{"status": "error", "message": …}` — это ответ самой функции,
а не шлюза. Без проверки поля `status` провал выглядит успехом.

**Права на действие роль получает только в момент создания действия.**
`custom_event.go:105` заводит строки `action_permission` для всех ролей,
какие есть на тот момент, а правка прав — UPDATE без вставки
(`permission.go:1690`). Роль, созданную позже, это не догоняет:
записи у неё нет, и завести её нечем — список действий в правах роли
собирается тем же `FILTER (WHERE ap.guid IS NOT NULL)`
(`permission.go:1735`) и приходит пустым.

**«Прав нет» и «запрещено» приезжают одинаково.** В списке действий
право подставляется как `COALESCE(ac.permission, false)`
(`custom_event.go:239`), поэтому роль без записи неотличима от явного
запрета — по самому `permission`. Отличает их пустой `id` записи:
на нём и держится правило «прячем только запрещённое явно»
(features/table/api/actions.ts, `isAllowed`).

## View

**PUT /v2/views отвечает дважды.** `h.HandleResponse` вызывается
и в ветке успеха, и после неё: в теле два JSON подряд, разобрать его
нельзя. Свежий view приходится брать перезапросом списка.

**POST /v3/menus/{id}/views — то же самое.** Поэтому view создаётся
ручкой `POST /v2/views/{table_slug}`, хотя принадлежит меню.

**Права на view: два похожих ключа, и настоящий только один.**

`attributes.view_permissions` (во множественном числе) в списке view —
не право, а наличие записи: бэкенд спрашивает `SELECT role_id FROM
view_permission WHERE view_id = $1 AND role_id = $2` и кладёт `true`,
если строка нашлась (`view.go:340`). Колонки `view`, `edit`, `delete`
он оттуда не читает вовсе, поэтому флаг врёт в обе стороны — у роли,
заведённой после view, он `false` без всякого запрета, а у роли,
которой просмотр отняли, остаётся `true`.

До клиента он вдобавок не доезжает совсем. View кладётся в ответ
на `view.go:304` (`Attributes: row.Attributes` — копируется указатель),
а флаг дописывается ниже переприсваиванием `row.Attributes, _ =
structpb.NewStruct(...)` (`view.go:351` и `:355`): это НОВЫЙ указатель,
и лежащий в ответе view по-прежнему смотрит на прежний объект. Там же
мёртв и разбор атрибутов на `view.go:330`: `attributes := []byte{}`
в список `rows.Scan` не входит, поэтому `len(attributes) > 0` ложно
всегда.

`attributes.view_permission` (в единственном) — настоящий объект
`{view, edit, delete}`. Отдаёт его только `POST /v1/table-details/{slug}`
(`object_builder.go:741`), по роли из токена, и по нему же работает
старая админка. Отсюда права на view и читаются.

**Роль без записи в `view_permission` роняет всю ручку.** Тот же код
берёт права через `QueryRow(...).Scan(...)` (`object_builder.go:726`)
и на отсутствие строки возвращает ошибку — не пустые права, а отказ
на весь `table-details`. Записи заводятся при создании view для ролей,
какие есть на тот момент (`view.go:178`), позже не появляются. Поэтому
«прав нет» доходит либо как отсутствие ключа, либо как отсутствие
ответа целиком, и запретом это считать нельзя.

**`default_limit` не обновляется.** В UPDATE view этой колонки нет,
поэтому «строк на странице» в настройках view мы не показываем вовсе.

**Настройки календаря не обновляются тоже.** В том же UPDATE
(`view.go:533`) пишутся только `table_slug`, `type`, `view_fields`,
`quick_filters`, `name`, `attributes`, `calendar_from_slug`,
`calendar_to_slug`, `group_fields` и `columns`. `disable_dates` задаётся
только при создании (`view.go:110`, INSERT), а `time_interval`
и `status_field_slug` не пишет вообще никто: во всём репозитории они
встречаются только в SELECT (`view.go:416`, `object_builder.go:616`).
Поэтому шаг сетки, нерабочие дни и цвет по статусу в CALENDAR мы читаем
и не даём настраивать.

**`time_interval` не приходит даже на чтение.** Список view пункта меню
(`GET /v3/menus/{id}/views` → `view.go:213`, GetAll) выбирает
`calendar_from_slug`, `calendar_to_slug`, `status_field_slug`
и `disable_dates`, но `time_interval` в этом SELECT отсутствует —
он есть только в `GetSingle` (`view.go:416`), ручки для которого
в шлюзе нет. То есть значения не видно ниоткуда и задать его нечем.
Шаг сетки в календаре поэтому постоянный, 60 минут
(`features/item/model/calendar.ts`, `SLOT_MINUTES`).

**PUT view всегда переписывает четыре колонки.** `calendar_from_slug`,
`calendar_to_slug`, `group_fields` и `columns` подставляются
безусловно (`view.go:625`), даже когда их не прислали. Тело собирается
поверх полученного view целиком — иначе переименование вкладки стёрло бы
поля дат и группировку.

**PUT view пересобирает `columns` по `attributes.group_by_columns`.**
`view.go:574` вынимает список из attributes, выкидывает эти id из
присланных колонок и ставит их в начало. Порядок колонок, заданный
мышью, после сохранения группировки меняется сам.

## Группировка

**Серверная группировка игнорирует фильтры и страницу.**
`builder_service_view_id` в теле `POST /v2/object/get-list/{slug}`
уводит запрос в `GetGroupByField` → `GroupByColumns`
(`ucode_go_object_builder_service/storage/postgres/object_builder.go:1977`).
Запрос строится как `SELECT поля_группы, jsonb_agg(…) FROM таблица
GROUP BY поля_группы` (`object_builder.go:2166`) — без `WHERE`, без
`LIMIT` и с коррелированным подзапросом на каждое LOOKUP-поле. Ни
фильтров, ни поиска, ни сортировки, ни `default_filters`: строки,
спрятанные областью видимости view, в сгруппированном ответе видны,
а таблица приезжает целиком одним ответом. Поэтому группируем на клиенте
(`features/item/model/group.ts`), а эту ветку не зовём.

**Пустой `attributes.group_by_columns` перекрывает колонку.**
`getViewGroupFields` (`object_builder.go:2072`) берёт список из
attributes и только при отсутствии ключа падает на колонку
`view.group_fields`. Ключ с пустым массивом — это присутствующий ключ,
поэтому view, созданный старой админкой (она кладёт
`group_by_columns: []` каждому новому view), получает отказ
«group_by_columns is required» даже с заполненной колонкой. Мы пишем
колонку, а ключ из attributes при сохранении удаляем.

## Доска

Пара ручек доски — `POST /v2/items/{slug}/board` и `.../board/structure`
— выглядит как готовый ответ на «дай карточки по колонкам», но ни одну
из трёх своих обязанностей не выполняет. Поэтому доска у нас собирается
из обычного get-list (`features/item/model/board.ts`).

**Порядок карточек, ради которого заведена `board_order`, ручка
не соблюдает.** `storage/postgres/object_builder.go:3226`:
`ORDER BY a.created_at DESC, a.board_order ASC, a.created_at DESC` —
без подгруппы сортировка идёт по `created_at`, а номер позиции
становится разрешением ничьих, которых не бывает. То есть карточку
можно перетащить, номер запишется, а на следующем запросе она вернётся
на прежнее место. (С подгруппой первым ключом становится поле подгруппы
— тоже не порядок.)

**Из фильтров понимает только «значение из списка».**
`buildBoardWhereClauseFromParams` (`object_builder.go:3145`) обходит
ключи тела и берёт из них ТОЛЬКО те, чьё значение — массив (`= ANY`).
Условия `{$in}`, `{$gte}`, подстрока и булево молча пропускаются.
Это не про удобство: `attributes.default_filters` — область видимости
view, и на доске она бы просто не применилась, показав строки, которые
view прячет.

**Страница считается по всей доске, а не по колонке.**
`buildBoardDataQuery` (`object_builder.go:3220`) — один `SELECT …
OFFSET $1 LIMIT $2` по таблице, а раскладка по колонкам делается уже
в Go из полученных строк. «Показать ещё» в отдельной колонке ручкой
не выражается. Заодно: `limit` не задан — это `LIMIT 0`, то есть пустой
ответ, а не «сколько получится».

**Колонка `board_order` заводится сама.** `storage/postgres/view.go:66`
и `:559` — при создании и при сохранении view типа BOARD бэкенд
проверяет наличие поля `board_order` и заводит его (`FLOAT`, см.
`pkg/helper/view.go:15`). Фронт её не создаёт и в списках полей
не показывает.

## Отбор строк

**Страницы get-list приходят внахлёст.** Порядок по умолчанию —
`ORDER BY a.created_at DESC` (`ucode_go_object_builder_service/storage/
postgres/build_query.go:130`), при `table_order_by` — то же по
возрастанию (`:199`), а явный `order` из тела собирается
`buildOrderClause` (`:274`) и `created_at` из него ВЫКИДЫВАЕТСЯ (`:283`).
Уникального ключа в порядке нет ни в одном из трёх случаев.

Postgres на неоднозначном `ORDER BY` не обязан выдавать одинаковый
порядок разным запросам, а `LIMIT/OFFSET` — это разные запросы. У
импортированной таблицы, где `created_at` одинаков у тысяч строк, куски
пересекаются: одна и та же строка приезжает в нескольких, а другая
не приезжает вовсе. Видно на таблице в два миллиона строк — одна запись
на экране трижды.

Чинится это только в бэкенде — добивкой порядка первичным ключом
(`, a.guid DESC`). Пока фронт отбрасывает повторы по guid при склейке
кусков (`features/item/api/items.ts`, `toPages`): показать одну запись
дважды нельзя, а пропущенные ею строки взять всё равно неоткуда.

Там же рядом: `order`, в котором ЕДИНСТВЕННОЕ поле — `created_at`,
собирает `ORDER BY ` без единой колонки (`:279` ставит начало, `:283`
выкидывает поле, `:39` подклеивает результат к запросу) — это уже
не порядок, а синтаксическая ошибка SQL. Мы это пока не задеваем
и не обходим; всплывёт — сортировкой таблицы по колонке создания.

**Условия «поле пусто» у get-list нет.** `buildComparisonFilters`
(`ucode_go_object_builder_service/storage/postgres/build_query.go:360`)
понимает ровно пять операторов — `$gt`, `$gte`, `$lt`, `$lte`, `$in`, —
а `buildFieldFilter` рядом добавляет к ним равенство и вхождение
в список. `IS NULL` не выражается ни одним из них: пустое значение
в теле даёт `= ''`, а это не то же самое, что «не заполнено».

**`$in` уходит в pgx нераспакованным списком.** `buildComparisonFilters`
(`build_query.go:373`) кладёт значение оператора в аргументы запроса как
есть: `qb.args = append(qb.args, v)`. После `ConvertStructToMap`
(`pkg/helper/helper.go:63` — это `json.Unmarshal` в `map[string]any`)
список из тела — всегда `[]interface{}`, а такого типа у pgx нет:

```
rpc error: code = Unknown desc = error while getting rows:
cannot use unregistered type []interface {} as query argument
in QueryExecModeExec
```

Соседние ветки того же файла оборачивают список в `pq.Array`
(`build_query.go:338` для голого списка, `:85` для `client_type`) —
забыта ровно эта. То же самое в v1: `object_builder.go:1275`.

Ещё два места с тем же дефектом, но мы их не задеваем: `additional_values`
(`build_query.go:74`) — этот ключ мы не шлём; `buildAutoFilters`
(`build_query.go:301`) — значения из прав роли, если там окажется список.

Кто у нас это задевает: условие `is` (`features/item/model/query.ts`,
`toCondition`) — точное совпадение по тексту и числу, отбор по связи
и вкладки раскладки (`features/view/api/tab-group.ts`, `tabFilter`).
Голый список (`{поле: [значение]}`) через ту же ручку проходит — именно
им отбирала вкладки старая админка (`Grid.jsx`: `[${groupTab.value}]`).

**Ключи `gte` и `lte` в теле get-list не делают ничего.** `applyFilters`
(`build_query.go:256`) разбирает только `limit`, `offset`, `order`
и `auto_filter`, а всё остальное отдаёт `buildFieldFilter`, который
молча выходит, если ключ не совпал со слагом поля. Старая админка шлёт
диапазон таймлайна именно так (`views/views/modules/Timeline/Timeline.jsx:149`)
— то есть её таймлайн не отбирает по датам вовсе и тянет таблицу
целиком. Диапазон задаётся только формой `{поле: {$gte, $lte}}`.

Задевает это таймлайн: записи БЕЗ дат — отдельный список, из которого
задачу ставят на ось перетаскиванием, а спросить их у ручки нечем.
Обходим порядком: `buildOrderClause` (`build_query.go:274`) собирает
`ORDER BY a.<поле> DESC`, а `DESC` в Postgres — это `NULLS FIRST`,
то есть пустые приезжают началом первой страницы. Приехавшее всё равно
проверяется по значению (`features/item/api/timeline.ts`): изменится
порядок — список опустеет, но не соврёт.

## Функции

**`/v1/invoke_function` отвечает пустым телом.** `InvokeFunction`
(`ucode_go_admin_api_gateway/api/handlers/v1/function.go:557`) зовёт
функцию и отдаёт `models.InvokeFunctionResponse{}` — пустой литерал:
ни `status`, ни `data`, ни ссылки. То есть результат функции наружу
не уходит вовсе: клиент узнаёт только, что вызов приняли (или что
принять не смогли — тогда приходит ошибка HTTP).

Отсюда две вещи. Первая: сообщение «действие выполнено» врало бы —
у нас оно теперь «действие запущено». Вторая: ветки, которые в старой
админке разбирали ответ функции (`res?.link`, `res?.status === "error"`
— `views/Objects/components/CustomActionsButton/ActionButton.jsx:59`),
не срабатывали никогда; свою мы оставили на случай, когда шлюз начнёт
ответ передавать, и подписали, что сегодня она мёртвая.

**Правка функции перезаписывает строку целиком.** `Update`
(`ucode_go_object_builder_service/storage/postgres/function.go:431`) —
это `SET` по двадцати колонкам сразу, без разбора заполненности.
Всё, чего не было в теле, обнуляется: `url`, `password`, `ssh_url`,
`gitlab_id`, `gitlab_group_id`, `error_message`, `pipeline_status`,
`is_public`, `max_scale`, `github_repo_name`, `github_webhook_id`.
То есть правка одного описания через собранное заново тело отвязывает
функцию от её репозитория и стирает адрес, по которому она отвечает.

Обход у нас тот же, что у полей таблицы: тело собирается поверх
исходного ответа (`settings/api/functions`, `useUpdateFunction`).
Чинить на бэкенде: собирать SET из заполненных полей, как это уже
сделано в соседнем `docx_template.Update`.

**Запуск функции: две ручки, и полезна вторая.**
`POST /v1/invoke_function` возвращает пустой `InvokeFunctionResponse{}`
всегда (см. выше). `POST /v2/functions/:function-id/run`
(`api/handlers/v1/function_v2.go:229`) ходит в саму функцию — OpenFaaS
или Knative — и отдаёт её ответ наружу, включая `message` из ошибки.
Обе живы, разница нигде не описана; действия таблицы зовут первую.

**Чтение исходников создаёт ветку.** `GET /v2/function/:id/codebase`
перед скачиванием архива проверяет ветку `u-gen` и СОЗДАЁТ её от
дефолтной, если не нашёл (`function_service/pkg/gitlab/gitlab.go:1137`,
`ensureUGenBranch`). То есть просмотр кода — операция с последствием
в чужом репозитории. Отсюда наше правило: запрос уходит только у
открытой карточки и не префетчится.

**Функции типа WORKFLOW не имеют репозитория.** В создании ветка
`case config.WORKFLOW` пустая (`function_service/api/handlers/
function.go:200`): форк не делается, `repo_id` остаётся нулём.
Поэтому у такой функции `codebase` отвечает `400 "function has
no linked gitlab repository"` — не ошибка, а следствие типа.

## Дерево

**`POST /v2/items/{slug}/tree` читает из тела ровно одно условие.**
`storage/postgres/ag_grid_tree.go:105` берёт `params["<slug>_id"]` —
родителя, — и на этом всё: рекурсивный запрос (`buildRecursiveQuery`,
там же:203) собирается из слага таблицы, списка полей, значения родителя,
limit и offset. Любые другие ключи тела молча отбрасываются.

**Автофильтр роли в дереве не применяется.** Он вычисляется
(`parseAndValidateRequest` зовёт `helper.GetAutomaticFilter`), кладётся
в `QueryContext.Autofilter` (`:55`) — и больше не читается нигде:
в `buildRecursiveQuery` его нет. То есть роль, которой `automatic_filter`
сужает выборку, в дереве видит строки целиком. Это уже не про дерево
во вкладке, это про права.

**Значение родителя подставляется в SQL строкой.** Там же, `:217` и `:267`:
`fmt.Sprintf("parent_node.%s = '%s'", childField, qc.FilterValue)` — без
параметра запроса. Значение приходит из тела, то есть от клиента. Мы шлём
туда guid, но ручка открыта, и внедрение SQL здесь возможно у любого,
кто до неё дотянется. Чинится в object_builder, не у нас.

Отсюда следствие для фронта: **дерево нельзя отобрать по связи**.
Вкладка связи в карточке показывает строки чужой таблицы, связанные
с открытой записью, — то есть условие по колонке-ссылке. Ручка его
не применит, и дерево во вкладке через неё показало бы всю чужую
таблицу.

Поэтому вкладка не ходит в эту ручку вовсе: строки она грузит обычным
get-list (с отбором, который тот понимает), а иерархию собирает
на клиенте — `groupByParent` в `features/item/model/tree.ts`. Строка,
чьего родителя в наборе нет, встаёт в корень. Цена: дерево видно
в пределах загруженной порции (100 строк).

Старая админка шлёт фильтры в ручку дерева и считает, что они работают
(`views/views/modules/Grid/useGridProps.jsx:632` — `...updatedFilters`
в теле). Не работают: её вкладка-дерево показывает таблицу целиком.

## Меню

**PUT /v3/menus пишет строку целиком.** `storage/postgres/menu.go:943`:
поле, которого нет в теле, обнуляется — переименование пункта стёрло бы
ему `table_id`. Тело собирается поверх пункта целиком.

**PUT /v3/menus не меняет `microfrontend_id`.** Шлюз его передаёт
(`api/handlers/v3/menu.go:344`), а SQL не пишет: в `UPDATE "menu" SET`
этой колонки нет вовсе (`storage/postgres/menu.go:944`, там только
label, parent_id, layout_id, table_id, type, icon, attributes). У этого
две стороны. Хорошая: переименование пункта не стирает приложение,
как стёрло бы `table_id`. Плохая: сменить приложение у готового пункта
нечем — только завести пункт заново. Поэтому список приложений
показывается в форме СОЗДАНИЯ и не показывается в форме правки:
переключатель, который ничего не переключает, — это то, за что
переписан старый конструктор.

**POST /v3/menus с type=TABLE не работает** — если `table_id` не задан.
Вставляет пустой пункт и тут же идёт искать слаг по несуществующему
`table_id`. Новая таблица создаётся ручкой `POST /v1/table`, которая
в одной транзакции заводит и таблицу, и пункт меню, и layout, и view,
и права. А вот пункт на УЖЕ СУЩЕСТВУЮЩУЮ таблицу — наоборот, только
`POST /v3/menus` с `table_id`: слаг находится, и пункту заводится
своя пара view, TABLE и SECTION (`storage/postgres/menu.go:113`).

**GET /v3/menus молча не умеет `search`.** Шлюз параметр принимает
и передаёт в gRPC (`api/handlers/v3/menu.go:249`), а в SQL он не
доезжает: в `WHERE` у `menuRepo.GetAll` только `table_id`, `parent_id`
и `role_id` (`storage/postgres/menu.go:692`), слова `Search` в файле
нет вовсе. Запрос с непустым `search` возвращает тот же уровень
целиком — то есть выглядит как поиск, который «ничего не отфильтровал».

Поэтому поиск по меню у нас клиентский: дерево дочитывается уровнями
вширь (`features/sidebar/api/menus.ts`, `useMenuTree`) и отбирается
в памяти. Починится на бэкенде — обход заменяется одним запросом.

## Шаблоны

**Строки чужой таблицы попадают в шаблон.** `POST /v1/template`
(`ucode_go_admin_api_gateway/api/handlers/v1/template.go`) объявляет
`rowsData` ВНЕ цикла по таблицам (строка 106), заполняет его только
у таблицы с `with_rows` (329), а кладёт в шаблон безусловно (345).
То есть таблица без флага, идущая следом за таблицей с флагом,
получает её строки.

Поэтому «со строками» у нас один флажок на весь шаблон, а не по
таблице: при `with_rows` у всех каждая перезаписывает `rowsData`
своими строками, при `with_rows` ни у кого он остаётся пустым.
Смешанного выбора мы не отправляем вовсе.

**Остальное шлюз собирает сам, и это хорошо.** По одному `id` таблицы
он дочитывает поля, связи, view, раскладки и действия, а по `menu_id`
— дерево пунктов (`template.go:210`). Собирать содержимое шаблона
на клиенте, как делала старая админка, не нужно: тело — это имя,
папка и список id.

## Печатные формы

**Любой ключ с «_id» в теле печати — это поход в таблицу с таким
именем.** `ucode_go_admin_api_gateway/api/handlers/v2/docx_template.go:830`
собирает `additional_fields` из присланных данных условием
`strings.Contains(key, "_id")`, а `ucode_go_object_builder_service/
storage/postgres/docx.go:474` по каждому такому ключу делает
`GetItem(ctx, conn, strings.TrimSuffix(key, "_id"), value)` —
`SELECT * FROM "<ключ без _id>" WHERE guid = $1`.

Промах — не пустая переменная в документе, а ошибка SQL, из которой
шлюз делает 500 на весь запрос. Промахнуться легко:

- `clients_ids` — Many2Many хранится колонкой `<таблица>_ids`
  (`relation.go:75`); «_id» в середине не отрезается, и таблицы
  «clients_ids» не существует: `relation does not exist`;
- `client_id` пустой — незаполненная связь: `cast.ToString(nil)` даёт
  пустую строку, а `WHERE guid = ''` это `invalid input syntax for
  type uuid`;
- `passport_id` — обычное текстовое поле, в слаге которого есть «_id»:
  таблицы «passport» не существует.

То есть печать сегодня ломается на половине живых таблиц, и ломается
целиком, а не по одной переменной. Обход у нас — `features/docs/
model/print-data`: ключ с «_id» уезжает, только если это поле LOOKUP
и в нём лежит uuid. Цена обхода: значения остальных таких полей
в документ не попадают.

Чинить на бэкенде: брать не «содержит _id», а поля типа LOOKUP из
схемы таблицы, и пропускать пустые значения.

**Правка docx-шаблона заново конвертирует файл, даже когда меняли
одно имя.** `UpdateDocxTemplate` при непустом `file_url` скачивает
файл, гонит его через стороннюю службу конвертации, кладёт docx и pdf
в minio под НОВЫМИ именами и подменяет обе ссылки
(`api/handlers/v2/docx_template.go:403–559`). Прежняя пара файлов
остаётся в хранилище сиротами, а вызов стоит конвертации.

Обход у нас: переименование отправляет только `id` и `title` —
пустые поля до базы не доходят, `Update` собирает SET из заполненных
(`ucode_go_object_builder_service/storage/postgres/docx_template.go:232`).
Чинить на бэкенде: конвертировать, только когда `file_url` ИЗМЕНИЛСЯ.

**HTML-шаблоны у postgres-проекта заводятся, но не печатаются.**
Обе ручки превращения — `POST /v1/html-to-pdf` и
`POST /v1/template-to-html` — имеют пустую ветку
`case pb.ResourceType_POSTGRESQL` с комментарием
`// Does Not Implemented` (`api/handlers/v1/view.go:97` и `:187`),
после чего ответ уходит с неинициализированным телом: `201` и пустая
ссылка вместо отказа. CRUD самих шаблонов (`/v1/html-template`) тип
ресурса не разбирает вовсе — уходит в mongo-сборщик всегда
(`api/handlers/v1/html_template.go:73`, `GetBuilderServiceByType`,
и она не возвращает `GoObjectBuilderService` ни при каком `nodeType`).

Обход у нас: пустая ссылка при коде 200 считается отказом и
произносится вслух (`features/docs/api/html-templates`, `useHtmlToPdf`).
Чинить на бэкенде: либо реализовать ветку, либо отвечать ошибкой —
`201` с пустым телом неотличим от успеха.

Заодно: старая админка зовёт эти ручки по адресу
`/v2/utils/export/{tableSlug}/html-to-pdf`, которого нет. То есть
HTML-печать не работает там ни на каком типе проекта — но причина
не в отсутствии маршрута, а в неверном адресе.

## Микрофронтенды

**Правка микрофронтенда не работает на PostgreSQL и портит данные
на MongoDB.** `UpdateMicroFrontEnd`
(`ucode_go_function_service/api/handlers/microfrontend.go:477`) собирает
`obs.Function` из семи полей — `id`, `name`, `path`, `description`,
`project_id`, `function_folder_id`, `type`, — и дальше расходится
по типу ресурса:

- MongoDB: этот объект уходит в `Function().Update` как есть. `Update`
  в object_builder — `SET` по двадцати колонкам сразу
  (`storage/postgres/function.go:431`), поэтому `url`,
  `environment_id`, `pipeline_status`, `error_message`, `is_public`,
  `max_scale`, `gitlab_id`, `gitlab_group_id`, `password`, `ssh_url`,
  `github_repo_name`, `github_webhook_id` обнуляются. Переименование
  стирает адрес сборки — то самое поле, по которому микрофронтенд
  показывается пунктом меню.
- PostgreSQL: в ветке объявлена НОВАЯ переменная с тем же именем —
  `var updateFunction = &nb.Function{}` (`:564`), — и следующая строка
  копирует её саму в себя: `MarshalToStruct(updateFunction,
  &updateFunction)`. Внешний объект затенён и до сервиса не доезжает;
  уходит пустая структура, без `id` и без `project_id`. Ручка отвечает
  ошибкой всегда.

Чинить: во второй ветке передавать внешний объект (переименовать
переменную), в первой — собирать SET из заполненных полей.

Обход у нас — не звать её вовсе: кнопки «переименовать» у
микрофронтенда нет, и в форме заведения об этом сказано.

**Шлюз не проксирует файлы микрофронтенда.** В сервисе есть и чтение,
и запись файлов рабочей ветки `u-gen` — `GET /v2/functions/
micro-frontend/files` и `PUT /v2/functions/micro-frontend/push-changes`
(`function_service/api/api.go:124–128`). В шлюзе группа
`proxyFunctions` перечисляет маршруты поимённо и этих двух не содержит
(`api/api.go:853–868`), а подстановочного маршрута в группе нет.
То есть из админки редактор файлов недостижим — при том, что
у микрофронтенда, в отличие от функции, ручка записи существует.

Показ файлов всё же возможен: `GET …/micro-frontend/files-at-commit`
проксируется, и он отдаёт снимок репозитория на любом коммите.

**Публикация требует проект MCP, а заведение его не ставит.**
`PromoteMicrofrontendToMaster` отклоняет запрос без `mcp_project_id`
(`microfrontend.go:969`), а `CreateMicroFrontEnd` это поле не
заполняет (`:232`) — его ставит только публикация из генератора.
Значит промоут доступен лишь микрофронтендам, пришедшим из генератора;
у заведённых руками кнопки публикации нет.

**История версий — это история из админки, а не из репозитория.**
`GetMicrofrontendCommits` берёт коммиты ветки `u-gen` и отсеивает те,
у которых почта автора не совпала с владельцем токена сервиса
(`microfrontend_commits.go:88`). Коммиты, сделанные человеком напрямую
в GitLab, в списке версий не появятся.

**Swagger над прокси не описывает ответ.** `GetMicroFrontEndByID`
и `GetAllMicroFrontEnd` (`api/handlers/v1/microfrontend.go:49` и `:68`)
— это `h.MakeProxy(c, GoFunctionServiceHost…)`: тело отдаёт
функциональный сервис, а аннотация `models.Function` над обработчиком —
просто комментарий. Форму ответа надо читать в proto: `Function`
(`new_function_service/new_function.pb.go:263`) — там и `Url` (поле 9),
и `SourceUrl` (16). Сам сервис теперь лежит рядом с остальными
(`ucode_go_function_service`), и его маршруты видно целиком —
`api/api.go:102` и `:113`.

Записано не ради ручки, а ради урока: истина о прокси-обработчике
не в его аннотации. По ней тип `MICROFRONTEND` был однажды помечен
«заблокировано бэкендом» — неверно.

## API-ключи

**Ограничения запросов не сохраняются ни одной ручкой.** Колонки
`rps_limit` и `monthly_request_limit` у `api_keys` есть (миграция
`ucode_go_auth_service/migrations/postgres/000036_alter_table_api_keys.up.sql`),
в proto они тоже есть — и в `CreateReq`, и в `UpdateReq`. Но INSERT
их не перечисляет вовсе (`ucode_go_auth_service/storage/postgres/
api_keys.go:36` — одиннадцать колонок, лимитов среди них нет),
а UPDATE пишет ровно четыре: `status`, `name`, `role_id`,
`client_type_id` (`api_keys.go:336`).

То есть значение из формы уезжает, ручка отвечает «сохранено»,
а в базе остаётся `2147483647` по умолчанию. В старой админке эти
два поля в форме ключа есть. У нас их нет: поле ввода, которое молча
ничего не пишет, — это то, за что переписан старый конструктор.

**Выключенность записана двумя полями, и пишутся они разными
ручками.** `disable` (boolean) заполняется ТОЛЬКО при создании,
`status` (`ACTIVE`/`INACTIVE`) — только при правке. Поэтому ключ,
выключенный при создании, включается правкой лишь наполовину:
`status` станет `ACTIVE`, а `disable` останется `true`. Читаем оба
и считаем ключ выключенным, если так сказало хоть одно
(`features/settings/api/api-keys`, `toApiKey`).

Вдобавок миграция `000042_create_table.up.sql:30` разом выключила все
существовавшие ключи (`UPDATE "api_keys" SET "disable" = TRUE`) —
в живом проекте почти все ключи помечены выключенными, и это не наша
ошибка отображения.

## Пользователи и приглашения

**Приглашения как сущности нет.** `/v2/user/invite`
(`ucode_go_auth_service/api/handlers/user_v2.go:507`,
`AddUserToProject`) не шлёт письма и не заводит запись «приглашён»:
она добавляет УЖЕ СУЩЕСТВУЮЩЕГО пользователя (`user_id`) в проект
с ролью и типом клиента. Ручки «отправить приглашение на почту»
в auth-сервисе нет вовсе.

Поэтому приглашение у нас — ссылка, которую копируют и отправляют
сами (`features/settings/model/invite`), ровно как в старой админке.
Пришедший по ней регистрируется сам — `/v2/register` с теми же
`project-id`, `env_id`, `role_id`, `client_type_id`.

## Типы клиентов

**Правка теряет `self_recover`.**
`ucode_go_auth_service/grpc/service/client_service_v2.go:364` кладёт
значение в тело под именем `self_recorder`, а колонка в
`client_type` называется `self_recover`
(`ucode_go_object_builder_service/migrations/postgres/
000001_init_tables.up.sql:26`). Object-builder пишет только те ключи,
у которых есть строка в `field` (`storage/postgres/items.go:641`),
поэтому опечатка не создаёт мусора — она просто ничего не меняет.
Прежнее значение остаётся целым.

Флажок «Восстановление пароля» показан только при СОЗДАНИИ: там путь
другой (`client_service_v2.go:47`, через proto с правильным именем)
и значение доезжает.

**Создание теряет `default_page`.** Там же, `client_service_v2.go:43`:
тело для object-builder собирается из девяти полей
(`CreateClientTypeRequestToObjService`), и адреса среди них нет —
в отличие от правки, где он есть (`client_service_v2.go:369`).
Поэтому «Страница после входа» есть в форме правки и её нет в форме
создания.

**Правка ВСЕГДА переписывает `confirm_by`.** Поле в
`V2UpdateClientTypeRequest` — enum, и его нулевое значение
(`UNDECIDED`) уезжает в базу, даже если в теле запроса поля не было.
Поэтому мы возвращаем сохранённое значение обратно числом
(`features/settings/api/client-types`, `CONFIRM_BY`), хотя сам
`confirm_by` не показываем: решений по нему никто не принимает —
в ответе входа он захардкожен нулём
(`ucode_go_object_builder_service/storage/postgres/login.go:357`).

**Имя с пробелом ломает автосозданную таблицу входа.**
`client_service_v2.go:72` заводит таблицу со слагом
`strings.ToLower(strings.ReplaceAll(name, " ", "_")) + "_users"`,
а в запись `client_type` кладёт `strings.ToLower(name) + "_users"`
(строка 96) — без замены пробела. У типа «Delivery Drivers» таблица
называется `delivery_drivers_users`, а тип ссылается на
`delivery drivers_users`, которой нет.

## Свои права (custom_permission)

**Только PostgreSQL.** `ucode_go_admin_api_gateway/api/handlers/v1/
custom_permission.go:242` — шлюз отвечает «resource type not supported»
всему, что не `ResourceType_POSTGRESQL`. На mongo-проекте вкладка «Свои
права» откроется и останется пустой; обойти это нечем.

**Доступ правится по одному.** `PUT /v1/custom-permission/accesses`
принимает ОДИН `custom_permission_id`
(`ucode_go_object_builder_service/storage/postgres/
custom_permission.go:298`), списка нет. Поэтому «Сохранить» на вкладке
шлёт по запросу на каждое изменённое право.

Пустая строка в `read`/`write`/`update`/`delete` означает «не трогать»
(там же, строка 311). Мы всегда шлём все четыре — иначе снятая галка
не доехала бы.

**Права появляются у роли только через два INSERT.** Заведение права
добавляет строку доступа каждой роли этого типа клиента
(`custom_permission.go:96`), заведение роли — каждому праву типа
(`storage/postgres/permission.go:605`). Список читается JOIN'ом
по `custom_permission_access`, поэтому право без строки доступа
не видно вовсе.

**`view_label`, `icon` и `type` не пишет ни одна ручка.** Вход их

## Журнал изменений (version_history)

**Опечатка в имени поля.** В proto поле называется `previus`
(`ucode_go_object_builder_service/protos/object_builder_service/
version_history.proto:39`), в SQL колонка — `previous`
(`storage/postgres/version_history.go:170`). Наружу уезжает имя
из proto. Читаем оба: `previus ?? previous`.

**Содержимое завёрнуто в `{"data": …}` и приезжает строкой.** Шлюз
оборачивает всё, что пишет в журнал (`api/handlers/v1/handler.go:192`),
а потом сериализует в строку. Внутри бывает объект, строка с текстом
ошибки или пустая карта — последняя означает «поля не было», а не
«объект без ключей». Разбор один: `features/settings/model/activity`.

**Отбора по окружению в запросе нет.** `GetAll` собирает `FROM
version_history WHERE true` и фильтрует только по типу, датам,
пользователю, ключу, действию и таблице (`version_history.go:109`).
Разделение по окружениям держится на том, что подключение берётся
по `resource_environment_id` — журнал физически лежит в базе
окружения. Это не проблема, но объясняет, почему записи соседнего
окружения не видны и почему `env_id` в параметрах ни на что
не влияет.

## Ресурсы проекта (project_resource)

**Список уже склеен из двух таблиц.** `GetProjectResourceList` —
это UNION ALL: строки `project_resource` плюс строки `resource`,
присоединённые через `resource_environment`
(`ucode_go_company_service/storage/postgres/resource.go:1626`).
То есть базы проекта в ответе v2 УЖЕ есть. Старая админка
дополнительно грузит их же из `/v1/company/project/resource`
и клеит три списка в один
(`SettingsPopup/modules/Resources/useResourcesProps.jsx:83`) —
и показывает каждую базу дважды.

**Порядка у списка нет.** В запросе нет `ORDER BY` вовсе. При этом
код подтверждения берётся из ПЕРВОГО ресурса типа
(`ucode_go_auth_service/grpc/service/session_service_v2.go:1104`,
`api/handlers/register_v2.go:266`). Два ресурса SMS в одном
окружении — и какой из них работает, не определено ничем.

**`type` при создании — число, при правке — строка.** Тело шлюз
читает обычным `ShouldBindJSON`, то есть `encoding/json`, а не
protojson. В `AddResourceToProjectRequest` поле `type` — proto-enum,
и «SMS» строкой валит разбор ВСЕГО тела
(`api/handlers/v1/project_resource.go:35`). В `ProjectResource`
(правка) то же поле объявлено строкой — там наоборот.

**Правка не меняет тип.** `UPDATE project_resource` пишет ровно три
колонки: `name`, `settings` и `external_id`
(`storage/postgres/resource.go:1846`). Присланный `type` не читает
никто.

**Правка затирает настройки целиком.** `settings = :settings`, без
слияния. Переименование ресурса, отправленное без настроек, обнуляет
учётку — в том числе выданную самим бэкендом (Superset, Metabase).

**Настройки системных строк подставляются под postgres.** Когда
`GetSingleProjectResouece` не находит строку в `project_resource`,
он читает `resource` и кладёт host/port/username/database
в `settings.postgres` — независимо от того, mongo это или clickhouse
(`storage/postgres/resource.go:1812`). Своего конверта у mongo нет.

**Удалить системную строку нельзя, а править — можно молча.**
`DELETE ... RETURNING id` по строке, которой нет в `project_resource`,
даёт `ErrNoRows` и 500; `UPDATE` не находит её и отвечает успехом,
ничего не изменив.

**Пустой список переменных приезжает одной пустой строкой.**
`JSON_AGG` по `LEFT JOIN` даёт `[{"id":null,…}]`, а не `[]`
(`storage/postgres/resource.go:1725`). Через omitempty до фронта
доезжает `[{}]`, и `variables.length` на такой строке врёт.

**Список переменных не отдаёт значения.** `GetVariableResourceList`
выбирает id, project_id, environment_id, key и project_resource_id —
колонки `value` в SELECT нет
(`storage/postgres/resource.go:1354`). Значения приходят только
в ответе на запрос одного ресурса.

**`false` в ответе переподключения выпадает.** `ReconnectResourceRes`
отдаёт по строке на службу с полем `status bool`
(`projects_service.proto:374`), а `omitempty` выбрасывает ложь.
«Служба не ответила» — это ОТСУТСТВИЕ `status`, а не `status: false`.
Заодно: ветки есть только у mongo и postgres
(`grpc/service/resource.go:1113`), у остальных типов ручка возвращает
пустой список и ничего не делает.

**Google Drive, Google Calendar, Telegram и Instagram отклоняются.**
Шлюз отвечает 400 со ссылкой на свою ручку подключения
(`api/handlers/v1/project_resource.go:56`, `:60`, `:64`, `:75`).
Telegram и Instagram не дают и удалить (`:729`, `:733`).

**Superset, Metabase и Transcoder игнорируют присланные настройки.**
Бэкенд заводит учётку сам и перезаписывает `in.Settings` своими
значениями (`grpc/service/resource.go:2546` для superset), а для
Transcoder создаёт компанию и проект в перекодировщике (`:2225`).
Поля формы в старой админке для этих типов отключены — и это верно.

**Ресурс POSTGRESQL — это подключение внешней базы.**
`AddResourceToProject` зовёт `CreateConnectionAndSchema`
(`grpc/service/resource.go:2582`) — ту же ручку, что и
`POST /v1/connections` (`api/handlers/v1/table.go:1333`). Разница
в том, что через ресурсы нет второго шага, выбора таблиц, без
которого подключение бесполезно.

## Права и middleware

**`AdminAuthMiddleware` прав роли не проверяет вовсе.** Имя обманывает:
это не «только супер-админ», а «без проверки прав». Обычный
`AuthMiddleware` зовёт `V2HasAccessUser`, и тот сверяет путь, метод
и таблицу с правами роли (`session_service_v2.go:2024`,
`checkPermission`). Соседний `HasAccessSuperAdmin`
(`session_service.go:295`) только разбирает токен, находит сессию
и пользователя — и возвращает данные сессии. Ни одной проверки прав
в нём нет, и флага «супер-админ» он тоже не смотрит: годится любой
живой токен.

Под этим middleware висит целая группа `/v2`
(`api/api.go:536`): логи функций, запуск функции, ресурсы проекта
(`/v2/company/project/resource`), печатные формы (`/v2/docx-template`)
и конвертер HTML. То есть роль без единого права дотянется до них
запросом напрямую — единственное, что стоит на пути, это наши же
кнопки. Из фронта это не чинится; здесь записано, чтобы никто
не принял отсутствие 403 за разрешение.

## View

**`function_path` только читается.** Колонка есть
(`ucode_go_object_builder_service/migrations/postgres/
000001_init_tables.up.sql:428`), её читают в пяти местах — настройки
связи, раскладка, секции, — и по ней поле связи должно брать варианты
не из таблицы, а из функции проекта. Но записать её нечем: во всём
сервисе она встречается только в списках SELECT (`view.go:234`, `:428`),
ни в одном INSERT и ни в одном UPDATE её нет.

То есть выпадающий список «Function» в форме связи старой админки
(`Constructor/Tables/Form/Relations/FunctionPath.jsx`) не сохраняет
ничего, а её же ветка чтения (`RelationField.jsx:265`) не срабатывает
никогда. Настройки у нас нет по этой причине, а не по забывчивости.
